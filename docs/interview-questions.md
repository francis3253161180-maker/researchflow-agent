# ResearchFlow 高频面试问题

回答原则：先给结论，再讲项目证据，最后说明边界。不要背成长篇论文。

## A. 项目总览

### 1. 这个项目解决什么问题？

普通 RAG demo 常缺少证据追溯、失败定位和可回归验证。ResearchFlow 将多格式解析、混合检索、状态编排、引用校验、有限重试和 SQLite 轨迹组成可部署服务，使回答可以回到页码/分节核对，也能定位失败节点。

### 2. 为什么它不只是聊天壳？

它包含真实文档导入、持久化知识库、检索排序、工具分支、状态循环、引用验证、运行轨迹、API边界、Docker和自动化测试，不是单次 prompt 调用。

### 3. 它是 Agent 还是工作流？

它是受控 Agent 工作流：会根据输入和知识库状态选择 RAG、计算工具或直接回答，并在引用失败后形成一次反馈循环。它不是开放式自主规划、多 Agent 协作或强化学习 Agent。

### 4. 你个人完成了什么？

建议按真实情况回答：需求定义、架构决策、实现组织、测试、文档和迭代均由自己主导；开发使用了 AI 辅助，但每个简历承诺都经过运行、测试和代码审查，面试中可以定位和修改关键模块。

## B. LangGraph 与 Agent

### 5. 为什么使用 LangGraph？

项目需要显式状态、条件路由、有限循环和节点轨迹。LangGraph 让这些转移成为可测试代码，也为未来 checkpointer 和人工审批留出扩展点。简单线性链当然可以不用它。

### 6. 图中有哪些节点？

`plan`、`retrieve`、`tool`、`answer`、`verify`、`persist`。固定边连接正常路径，条件边负责 plan 分支和 verify 重试。

### 7. plan 是如何做的？

当前是规则式：检测算术表达式走 tool；否则有 chunks 走 RAG；空知识库走 direct。它稳定可解释，但对复杂意图不足。

### 8. 为什么最多重试一次？

第一次失败后用固定词扩展查询，可能补回方法/结果/结论类证据；继续循环收益不确定且增加延迟和成本，所以业务层只允许一次，框架层另有 recursion limit 兜底。

### 9. 什么是 checkpointer？为什么没用？

Checkpointer保存图状态以支持恢复、暂停、线程状态和 human-in-the-loop。V1已把最终运行轨迹写入SQLite，但没有实现图级恢复；本地短请求暂不需要，长任务/人工审批时再引入。

### 10. Function Calling 与 MCP 有什么区别？

Function Calling 是模型输出结构化工具调用的能力；MCP 是客户端发现和调用外部工具/资源的协议。ResearchFlow 同时保留应用内的 calculator，并实现了独立 MCP Server：外部 Host 可通过 `search_research_documents`、`get_citation_context`、`calculate_expression` 和文档 Resource 访问本地知识库；应用内 LangGraph 则继续直接调用 Python 工具函数。二者解决的边界不同。

## C. RAG 与检索

### 11. 为什么同时使用 BM25 和向量检索？

BM25对术语、缩写、型号和精确词稳定；向量检索对同义改写更稳。二者失败模式不同，融合后召回更稳健。

### 12. 为什么用 RRF？

BM25和cosine的原始分数尺度不同。RRF只使用各自排名，避免分数归一化和权重调参，适合小型、后端可替换的V1。

### 13. RRF 的局限？

忽略原始分数差距，排名较差的列表也会贡献；没有学习任务相关权重。数据充分后可比较加权融合或学习排序。

### 14. 当前 BM25 是标准实现吗？

是BM25风格公式，使用 `k1=1.5`、`b=0.75`；中文按单字tokenize，没有成熟搜索引擎的分词、字段权重和倒排索引，因此不能称为完整生产BM25服务。

### 15. 为什么默认 HashEmbedding？

为离线测试提供确定、快速、无下载依赖的向量后端。它只验证接口和流程，不能代表真实语义检索。演示语义能力应切到 FastEmbed/BGE。

### 16. FastEmbed 为什么不需要 GPU？

当前小型 BGE 模型通过 ONNX Runtime 在 CPU 运行。GPU可能提高吞吐，但本地单用户演示不是必须。

### 17. 为什么没有 Reranker？

V1先验证解析、召回、引用和轨迹闭环。Reranker会增加模型下载和延迟；应先用标注集证明top-K排序不足，再作为可开关精排层加入。

### 18. chunk size 为什么是620、overlap为什么是80？

这是适合本地演示的启发式起点，不是通用最优值。它优先合并段落，长段落才滑窗。正式选择应在具体语料上用Recall@K、答案质量和token成本评测。

### 19. 十万篇文档时哪里先出问题？

当前每次检索加载全部 chunks、解析JSON向量、重新计算词法统计并线性扫描向量，时间和内存首先失控。需要离线索引、倒排检索、向量数据库、批量异步导入和独立存储。

## D. 引用、安全与失败

### 20. verified=true能保证答案正确吗？

不能。它目前只保证RAG有citations且回答含至少一个合法编号。它不验证每个主张是否被证据蕴含。真实忠实度需要逐句attribution、NLI/LLM judge和人工标注评测。

### 21. 如何处理文档提示注入？

system prompt明确把文档作为不可信证据而非指令；工具白名单和规则路由不让文档直接触发任意工具。但这只是基础防护，还需内容隔离、输出策略、红队样例和权限控制。

### 22. 为什么保存脱敏错误？

运行轨迹需要知道失败类型，但保存上游响应可能泄露请求、密钥或路径。因此当前只保存如 `llm_error: RuntimeError` 的类型信息。

### 23. calculator 为什么比 eval 安全？

它用AST白名单只允许数字和有限运算符，并限制指数；不允许属性访问、函数调用、导入和任意Python语句。

## E. FastAPI、SQLite 与工程

### 24. 为什么用 SQLite？

V1是本地单用户、小规模资料，SQLite零运维、事务清楚、便于演示和测试。多实例、高并发写和大规模向量检索时迁移PostgreSQL/专用向量库。

### 25. WAL 有什么作用？

写入先追加WAL，读通常不必等待写事务完成，提高读写并发；但仍不能把SQLite当成无限扩展的服务数据库。

### 26. 如何保证删除文档时 chunks 一起删除？

chunks的document_id外键设置 `ON DELETE CASCADE`，每次连接启用 `PRAGMA foreign_keys=ON`。

### 27. 为什么 embedding 存 JSON？

实现简单、便于V1查看和迁移；缺点是空间和解析成本高、无法高效索引。规模增长后应使用向量列或专用向量库。

### 28. 当前 API 有哪些保护？

Pydantic长度校验、上传类型和大小限制、可选API Key、constant-time比较、脱敏错误、文档不可信提示。仍缺用户权限、速率限制、TLS和审计策略。

### 29. Docker Compose 做了什么？

构建服务镜像、映射8000端口、注入模型/embedding/安全配置，并把数据库和模型缓存持久化到named volume。

### 30. CI 做了什么？

push/PR到main时，独立job运行Python 3.12下的pytest并构建Docker镜像。它验证可测试和可构建，不负责部署。

## F. 测试与评测

### 31. 18项测试覆盖什么？

图路由、引用重试、模型异常脱敏、混合检索、分块、PDF页码、Markdown分节、DOCX解析、环境变量优先级、端到端API、上传/删除、API Key和UI关键能力。

### 32. 8/8回归集表示什么？

表示固定样例在当前后端下完成预期字符串命中、引用和校验，用于防回归；语料来自项目说明，不代表真实企业准确率。

### 33. 下一步怎么做正式评测？

选择可公开语料，人工标注query、相关chunks和答案证据；报告Recall@K、MRR/nDCG、faithfulness、answer relevance、延迟和失败分布，并与纯BM25、纯向量、混合检索、加reranker做对照。

## G. 反问与边界题

### 34. 这个项目最大的不足？

当前验证集小且受控；检索线性扫描；引用验证较浅；PDF仅文本层；同步导入；没有图级checkpointer和正式生产鉴权。已实现可选 BGE reranker，但在当前 CPU 上延迟高，默认关闭。

### 35. 下一步只允许做一项，你做什么？

优先构造人工标注的真实论文问答/证据集，先量化召回和引用忠实度，再决定加reranker、改chunk还是换向量库。没有评测先加组件，难以证明收益。

### 36. 为什么面试官应该相信你理解项目？

通过现场画图、从API走到state和数据库、解释失败案例、修改一个节点/测试并跑回归来证明，而不是只背README。
